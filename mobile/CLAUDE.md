# BuyWise Mobile

Expo / React Native client for the BuyWise backend (FastAPI + Supabase, in the repo root: see [`../AGENTS.md`](../AGENTS.md)). This file describes the app as it is in the code today and is the operating reference for coding agents. Prioritize mobile-first patterns, performance, and cross-platform compatibility. The rulebook every change follows is [`../BUYWISE_MOBILE_GUIDE.md`](../BUYWISE_MOBILE_GUIDE.md); its "Suggested Structure" is aspirational, the real layout is under [Layout](#layout).

## Keeping this file current

- The code is the source of truth. When this file and the code disagree, change this file (never the code), in the same change as the feature or fix.
- `AGENTS.md` and `CLAUDE.md` in this folder are identical, because different coding agents read different ones. Edit both together; `diff AGENTS.md CLAUDE.md` must print nothing.
- Write only what you verified in the code. If the code cannot answer something (plans, intent, scope), ask the owner instead of guessing.
- After a feature adds, removes or changes a screen, an API call, a dependency or a convention, update [Status](#status) and any section it touches.

## Commands

```bash
npm install
npx expo start              # dev server (Expo Go, or press w for web)
npm test                    # node --test src/lib/*.test.ts (Node's built-in runner, no Jest)
npx tsc --noEmit            # typecheck
npx expo lint               # lint
npx expo-doctor             # diagnose dependency and config issues
npx expo install <package>  # ALWAYS use this to add a package: resolves SDK-compatible versions
npx expo install --fix      # fix incompatible package versions
```

Run tests, typecheck and lint before declaring any task done. New logic in `src/lib` gets a `*.test.ts` beside it. A feature is done when its loading, empty, error, validation, offline, keyboard and Android-back behavior work too (full list: the guide).

## Layout

- `src/app/`: Expo Router routes. Every file is a screen and `_layout.tsx` files define navigators; keep non-route code out of it. The signed-in / signed-out route guard (`Stack.Protected`) is in `src/app/_layout.tsx`.
- `src/ui/`: the v3 kit (below). It is the only code that reads `tokens.ts` (a copy of `design/theme.ts` plus an `extra` block of values from `design/reference-html`); screens import from `@/ui`, which does not export it.
- The v3 kit in `src/ui/` (DESIGN.md §3). Screens pass it lucide icons from `icons.ts` (`@/ui/icons`; Rule 5).
  - Layout and surfaces: `Screen` takes `surface` (`screen`, the charcoal default, `sage`, `peri`, `cream`; 18 side / 8 top / 12 between blocks, a light refresh spinner; `sage` sets dark status-bar icons, `screen` and `peri` light ones, and `cream` sheets leave the bar as the screen under them has it; the content column is capped at `space.contentMax` (600) and centred, and the frame pads the left and right insets for a rotated foldable or tablet. The tab bar row, `OptionSheet` and the `Fab` use the same cap, and the Goals `Dial` scales down on a narrow screen), `tabBar` (a tab root: content clears the floating bar), `fab` (a `Fab`, with room to scroll clear of it) and `enter` (the card entrance, see Motion below). ## Rules

1. **Data goes through `queries.ts` / `mutations.ts`.** Screens never call `api` directly. `invalidateAfter()` in `queries.ts` is the only place that knows which caches a write makes stale; a new kind of write adds a `Change` case there.
2. **Errors:** never render `err.message`; use `userMessage(err, "save this expense")`. A 404 on delete or update means "already gone" (`isNotFound`). A batch stops on `stopsBatch` errors (offline, signed out, rate limited).
3. **Money is integer minor units (paise).** Parse typed text only with `src/lib/money.ts`, total with `sumMinor`, never add `display_*` floats, and show amounts with `formatCurrency` / `formatMinor`. Amount fields use `EntryAmount`, whose `sanitizeAmountInput` reads a lone comma as the decimal point only when 0 to 2 digits follow it ("12,50"); otherwise it is grouping and is dropped ("12,000" becomes 12000).
4. **Dates are local calendar `YYYY-MM-DD`** computed on the phone (`todayLocal`, `rangeFor`, `monthShift`). List queries send explicit `date_from` / `date_to` because the server's own "this month" follows its UTC clock. The Dashboard is the exception: it sends `period=this_month` (the app no longer asks for `last_month`) and the phone's `today`, so the server resolves "this month" on the user's calendar. `dashboardQuery` puts the month of `today` in the cache key: a new month never shows the last one's figures, and a copy kept from an earlier day of the month still opens Home.
5. **Visuals live in `src/ui`.** A new look becomes a primitive there, not inline styles in a screen. Text uses the `tokens.ts` type styles and families (Barlow Semi Condensed, JetBrains Mono), whose weight is in the family name: never set `fontWeight` (Android fakes it). A category's colour comes only from `lib/categoryStyle.ts` `categoryHue` (through `CategoryTile` / `categoryTone`), and its glyph from its `icon` keyword (`CategoryTile`). Icons come from `@/ui/icons` (`./icons` inside the kit), one file per icon; a new icon gets a line in `src/ui/icons.ts`. Lint rejects value imports from `lucide-react-native` itself, whose index would put all ~1,850 icons back in the bundle (type imports such as `LucideIcon` are fine).
6. **Pure logic in `src/lib`** is import-free or imports siblings with an explicit `.ts` extension, so `node --test` runs it without a bundler. A module that imports `@/...`, React or React Native cannot be tested that way.
7. **Every data screen handles Loading (`Skeleton`), Success, Empty (`EmptyState`) and Error (`ErrorState` with retry).** If cached data exists and a refresh fails, keep showing it with `Banner tone="warning"` ("Couldn't refresh. Showing ..."; Home adds how old the numbers are, from `shownFreshness`). Tab roots support pull-to-refresh and `useRefetchStaleOnFocus()`.
8. **Forms and writes:** guard unsaved input with `useDiscardGuard`; destructive actions go through `confirm()`; success is `hapticSuccess()` plus `showToast()`. Writing buttons use `requiresNetwork` and are disabled while pending; that guard stops a double tap, and `POST /transactions` takes an `idempotency_key` (`add-transaction` sends one) so a retry after a timeout cannot double-log. Other creates (goals, categories, payees) have no key.
9. **Routes that take an id from the URL** validate it with `isUuid()` and show `NotFoundScreen` otherwise.
10. **Auth:** Google sign-in uses PKCE (`lib/googleAuth`, `lib/oauthCallback`) and a public `auth/callback` route; the Supabase redirect allowlist needs `buywise://auth/callback` and each web callback (see `../docs/GOOGLE_AUTH.md`). A native development/installed build is required for Google; Expo Go supports email/password. The session is kept in SecureStore (split into chunks because values can exceed ~2 KB; web falls back to localStorage). On a 401 the client refreshes the token once (single-flight), retries once, then signs out locally; a refresh that fails on the network is status 0, never a sign-out; `SIGNED_OUT` clears the whole query cache and deletes the copy kept on the phone. Credentials never go in that copy or the query cache: the session lives only in SecureStore. Supabase is used for authentication only: all data goes through the FastAPI API with `Authorization: Bearer <access token>`, and the `anon` / `authenticated` database roles have no table privileges, so never query Supabase tables directly.
11. **Network:** `networkMode: "always"`. `useOnline()` means only "no connection at all" and drives the offline banner and `requiresNetwork` buttons. Default `staleTime` 5 minutes (`FRESH_FOR` in `lib/cachePolicy.ts`; the profile 10 minutes; one transaction, category or payee 0, so a detail screen always confirms), one retry except on 4xx, no refetch on reconnect (it only marks data stale). Every write marks what it changed stale at once (`invalidateAfter`, and `changesFromChat` for AI chat), so the 5 minutes only delay changes made elsewhere (the web app, another phone); pull to refresh fetches them at once. **Kept on the phone:** the queries `queries.ts` marks `saved` (`meta.saved` and a 7-day `gcTime`: the dashboard, recent transactions, and the category and payee lists, nothing else) are written to `query-cache.json` in the cache folder (backups skip it; the OS may empty it) a second after one changes. The file is stamped with the user id and the app version (`app.json` `version`), restored only for that user and version, drops answers over 7 days old (`SAVED_FOR`) and is deleted on sign-out. Restored answers come back marked stale, so the first screen to show one also asks the API. Native only (the web build keeps memory alone). Bump `SAVED_VERSION` in `cachePolicy.ts` when a saved query's response shape changes. Timeouts: 15 s for CRUD, 90 s for chat, 15 s for each Supabase auth request (`fetchWithTimeout` in `supabase.ts`: React Native's Android HTTP client has none), 10 s to read the token before a request (`currentToken`; a timeout is status 0, which is retried once) and 8 s for the app's start to read the session.
12. **Comments:** short tags (`C4`, `L3`, `A1`, ...) mark edge cases handled on purpose, so keep them intact when editing nearby code. A `ponytail:` comment marks a deliberate shortcut and names its ceiling and upgrade path; read it before changing that code.

## Backend contract the client relies on

The API lives in `../ai_service/` (details in `../AGENTS.md`). `src/lib/types.ts` mirrors its response shapes by hand (no codegen): when a backend schema or route changes, update `types.ts` and `api.ts` in the same change.

- **One balance, no accounts or transfers.** The Dashboard's `current_balance` is income + starting balances - expenses. Each transaction has an optional `payment_method`: `cash`, `upi`, `bank_transfer`, `card` or `other`.
- **Amounts** are integer minor units; every money field also has a `display_*` float for display only.
- **Transaction types** are `expense`, `income` and `starting_balance`. Expense and income need a category of the same type. The add form offers Expense and Income only; a starting balance can be viewed and edited but not created in the app.
- **Categories and payees** are per user and seeded on the first `GET /profile` (36 each). A category's `type` cannot change. `DELETE /categories/{id}` archives it (hidden from lists, still shown on old transactions and budgets). `POST /categories` and `POST /payees` return the existing row when the name already exists, and `payee_name` on a new transaction finds or creates the payee. A category's `color` is saved as one of the 8 hue `bar` hexes in `lib/categoryStyle.ts` (what the web's swatches write too); the seeded rows carry other hexes, which the app replaces with the seeded name's hue, and icon keywords (`food`, `transport`, ..., one per seeded category). A category's glyph is its `icon` keyword's, else its seeded name's, else a tag, and the category editor's picker saves one of those 36 keywords.
- **Budgets:** `POST /budgets` is an upsert per category and month; `GET /budgets/YYYY-MM` returns, per row, `spent`, `remaining` and `percent_used` (this month's alone) plus `carried_in` and `available` (the rollover), and next to the rows `carried` (categories that carry money in but have no budget this month), `opening_balance`, `closing_balance` and `unassigned` (closing balance minus the money in every envelope: LEFT TO BUDGET). Only active expense categories can be budgeted.
- **Goals** have no GET-by-id and no DELETE. The app finds a goal in the cached Active / Achieved lists, and archiving (`PATCH status=archived`, on the Edit screen) is the removal path. The server sets `status` to `completed` when `current_amount >= target_amount`, and back to `active` if it drops below, unless a `status` is sent or the goal is archived. Contributing sends `current_amount = cached + amount` (there is no atomic contribute endpoint), so two devices contributing at the same moment lose one; this is deliberate and marked with `ponytail:` in `goals/[id]/contribute.tsx`.
- **Dashboard:** `GET /dashboard?period=&today=YYYY-MM-DD`; `today` is the phone's date (the server's UTC date is a day off near a month boundary). The response also has `opening_balance` and `closing_balance` for the period's month and `unassigned` (the same figure as LEFT TO BUDGET), plus `total_budgeted`, `total_spent`, `remaining_budget` (this month's budgets minus all of this month's spending) and `days_remaining_in_month` (today not counted); `current_balance` is the live balance and never resets at month end. Home's Safe to spend uses all four: the lower of `remaining_budget` and `current_balance`, over the days left.
- **Account deletion:** `DELETE /profile` answers 204 with no body (`fetchAPI` returns `undefined`). It deletes the user's data and then their Supabase login, and needs `SUPABASE_SERVICE_ROLE_KEY` on the backend: without it the answer is 503 and nothing is deleted, and a 502 means the data went but the login did not, so repeating is safe.
- **Transactions list:** `limit` 1 to 100 (the app uses 20), `offset`, and filters `transaction_type`, `category_id`, `payee_id`, `cleared_status`, `date_from`, `date_to`, `period`.
- **Limits and failures:** the API rate-limits per access token, or per IP when there is none (defaults in `ai_service/core/config.py`: 60 per minute for financial routes, 30 for profile, 20 for chat), and a 429 carries `Retry-After`. A 409 is a conflict (duplicate or racing insert); a 401 carries `WWW-Authenticate: Bearer`.
- **Chat:** the backend admits at most `CHAT_MAX_CONCURRENT` requests per process (default 4); excess requests return 503 with `Retry-After: 5` before saving a message. `api.chat` (90 s timeout), `listConversations` (History shows the 50 newest), `getMessages` and `deleteConversation`; `MSG.busy` is the 409 "Still processing". A message is at most 4000 characters and an agent turn can take up to 60 s. Each new send gets a fresh `idempotency_key` (`newIdempotencyKey`), and a retry of a failed send reuses its key: the server replays a finished send, answers 409 while it is still running and reruns a failed one. `getMessages` returns the newest page in chronological order; the app asks for 500 rows and has no "Load earlier" (`ponytail:` in `queries.ts`). History rows carry no tool calls and reasoning is not stored, so the tool pill and "view reasoning" show only on the reply that just arrived. A tool pill's label is `toolSummary` (parsed from the tool's JSON output, falling back to the tool name); the raw input and output stay behind the expander. `useSendMessage` writes both messages into the thread's cache in the hook options (so they land even if the user left the screen), then invalidates `conversation` plus the `changed_resources` named by the reply (`changesFromChat`: transactions, payees, budgets, goals). A replay has no tool details but still carries these resource kinds. History won't delete a conversation whose reply is still on its way.

## Environment and running

1. Copy `.env.example` to `.env.local` (gitignored via `.env*.local`) and fill in `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY` (the anon / publishable key only, never a `service_role` key) and `EXPO_PUBLIC_API_URL`. The app throws at startup if any is missing. Never commit real values or paste them into docs. Optional: `EXPO_PUBLIC_PRIVACY_URL` and `EXPO_PUBLIC_TERMS_URL`, the public pages the owner hosts (the stores require a privacy policy); a link whose URL is unset is not shown. Restart Expo with `npx expo start -c` after changing them.
2. `EXPO_PUBLIC_API_URL` must be the PC's LAN IP (`ipconfig`), not `127.0.0.1`, because a phone cannot reach the PC's loopback. Use `https://` for anything except local development.
3. Start the backend so the phone can reach it, from the repo root: `uv run uvicorn ai_service.main:app --reload --host 0.0.0.0`.
4. The phone and PC must share a network that allows device-to-device traffic (campus Wi-Fi often does not; use a phone hotspot). If Expo advertises the wrong adapter (VPN, VirtualBox), set `REACT_NATIVE_PACKAGER_HOSTNAME` to the LAN IP.
5. Supabase email confirmation must be off (or real SMTP configured), otherwise sign-up shows "Check your email".

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json` (currently 58).
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.
